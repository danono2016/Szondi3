# SZONDI3 — PROJECT MISSION

**Status:** ORIENTATION / MISSION COMPASS  
**Purpose:** keep every new collaborator and chat aligned with the clinical purpose of the project before engaging governance machinery.

## Mission

Szondi3 exists to become a real, versatile, trustworthy clinical instrument for psychotherapeutic practice.

Its epistemic foundation exists to make that instrument faithful, safe, traceable and repairable. The foundation is not the product, and governance is not the mission.

The practical direction is:

`Administration -> Deterministic Calculation -> Szondian Exploration -> Traceable Interpretation -> Longitudinal Comparison -> Clinical Integration -> Clinician Working Report`

The near-term product target is **Cabinet Alpha**: a real protocol can traverse this path end to end while observation, calculation, doctrine, executable interpretation, uncertainty and clinician synthesis remain visibly distinct.

## What must remain non-negotiable

1. Primary Szondi sources remain the highest doctrinal authority.
2. Canonical TXT is an access/provenance derivative; original PDF remains the visual arbiter where needed.
3. Doctrine and executable interpretation remain separate objects.
4. Downstream software may not rewrite upstream evidence or doctrine.
5. The system may preserve or reduce certainty, never inflate it beyond the source/evidence ceiling.
6. Ambiguity, contradiction and unsupported cases are preserved or fail closed rather than being narratively smoothed.
7. Clinical judgment remains human. Software can preserve, calculate, link, compare and structure evidence; it does not impersonate the clinician.
8. Identifiable patient data does not enter the repository.

These are the protections that make the clinical instrument trustworthy.

## Complexity and governance rule

Apply the Constitution's complexity rule literally:

> Complexity is introduced only when demanded by the source or by a demonstrated software requirement.

Documentation, audit and governance must be proportional to actual epistemic, software or clinical risk.

**Audit appears where risk requires it; it must not automatically precede every action.**

A UI improvement, navigation change or other low-risk tooling change does not require re-auditing the entire epistemic chain. A scoring rule, doctrinal representation or clinically consequential executable claim does require review appropriate to that layer and consequence.

Do not build preventive meta-governance merely because it might be useful later.

## Gates are validity markers, not the mission

Phase gates record what has been demonstrated. They prevent later work from being used as false authority for an earlier unfinished layer.

They are not the primary unit of product progress.

An unfinished earlier gate does not by itself prohibit downstream clinical prototyping when the foundation allows it, and it does not automatically dictate the next useful task. The relevant question is whether the downstream work depends on an unsupported upstream claim.

Formal gate state and active clinical development path must therefore remain distinguishable.

## Practical prioritization rule

For proposed work, ask first:

> **Does this make the instrument more useful, more faithful, or safer for real clinical use?**

If the answer is no, defer it unless it is required to remove a concrete blocker.

When a clinical feature encounters missing doctrine, ambiguity or an under-specified rule, return to the relevant source/layer and resolve exactly that dependency. Let documentation serve development rather than replacing it.

## Repair rule

When something is wrong, repair it in the lowest layer where the error originates:

- source-access error -> canonical access;
- scoring error -> deterministic engine;
- misrepresented Szondi statement -> doctrine registry;
- over-permissive activation -> executable interpretation;
- bad synthesis -> integration;
- poor wording -> reporting.

Do not answer a local problem by creating a new project-wide control structure unless the problem demonstrably requires one.

## New-chat orientation

A new chat or collaborator should understand this mission before reading takeover/governance procedures.

The repository remains durable project memory, but continuity mechanisms exist to preserve the work, not to dominate it.

Cold-start qualification, earthquake tests, broad repository audits and similar procedures are appropriate when state is genuinely uncertain, authority is changing, a high-risk layer is being modified, or evidence gives reason for doubt. They should not become ceremonial prerequisites to every useful task.

## Working maxim

> **Preserve Szondi. Build the clinical instrument. Apply rigor where consequence requires it.**

The project succeeds when the foundation disappears into the background and reliably supports a clinician-facing tool that can be trusted, inspected, corrected and used in real practice.
